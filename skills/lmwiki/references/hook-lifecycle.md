# 스킬 기반 기억과 runbook 생명주기

## 실행 경계

Codex `Stop`은 응답 하나가 끝났다는 런타임 신호일 뿐 사용자 작업의 종료가 아니다. LMWiki는 Stop 훅에서 기억을 자동 저장하지 않는다. 현재 작업에 `lmwiki` 스킬을 적용한 LLM이 대화, 남은 작업, 검증과 사용자 의존 항목을 보고 작업 단위의 완료 후보 여부를 판단한다.

## 완료 확인 순서

1. LLM은 현재 사용자 요청 전체에서 아직 직접 수행할 수 있는 일이 남았는지 확인한다.
2. 승인·선택·추가정보를 기다리거나 사용자가 후속 작업을 예고했다면 저장 질문을 하지 않는다.
3. 완료 후보이면 결과 보고 끝에 `이 작업을 마친 것으로 보고 기억을 저장할까요?`라고 한 번 묻고 `저장하기`와 `계속 작업`을 안내한다.
4. 이 질문을 한 턴에는 L0–L3 파일을 만들거나 갱신하지 않는다.
5. 사용자가 다음 메시지에서 `저장하기`, `네`, `맞아요`처럼 독립된 짧은 긍정 답변으로 확인한 경우에만 기억 저장을 시작한다.
6. 긍정 표현 뒤에 추가 지시가 붙으면 저장 승인이 아니라 계속 작업으로 처리한다. `계속 작업`, 부정 답변 또는 새 요청도 기억을 저장하지 않는다.

## 확인 뒤 처리 순서

1. L0: 확인받은 작업 단위의 사용자 원문과 도구 근거를 private memory로 캡처한다.
2. L1: L0에서 다시 쓸 가치가 있는 사실·선호·제약·사건을 원자 단위로 증류한다.
3. L2: 프로젝트나 업무를 재개할 때 복원할 장면을 L1에서 구성한다.
4. L3: 같은 subject의 활성 L1/L2 근거가 최소 두 개일 때만 독립성을 검토하고 Persona 생성 여부를 결정한다.
5. runbook 제안: 완료·commit·push·pull request 또는 반복 가능한 운영·복구 작업의 완료 신호가 있으면 별도로 생성 여부를 한 번 묻는다.

`memory.capture`의 기본값은 `explicit`이다. 개인·제한 기억은 Git에서 제외된 `.knowledge/private-memory/`에 둔다. L0의 provenance는 확인 답변 턴이 아니라 사용자가 완료를 확인한 원래 작업 단위를 가리킨다.

## runbook의 별도 승인

기억 저장 확인은 runbook 생성 승인이 아니다. 인수인계 경계 신호가 있으면 `이번 작업을 인수인계용 runbook으로 남길까요?`라고 별도로 묻는다. 사용자가 `만들기`를 선택한 뒤에만 `draft`를 만들고, 사람의 확인 전에는 `active`로 바꾸지 않는다.

## 비활성 훅

전역 `SessionStart`, `UserPromptSubmit`, `Stop`, `SessionEnd` LMWiki command 훅은 기본 설치와 실행 경로에서 사용하지 않는다. 이전 설치 파일이 남아 있어도 `hooks.json`에 등록되지 않으면 실행되지 않는다.
