# 훅 기반 기억과 runbook 생명주기

## 실행 순서

Codex `Stop` 훅은 작업 본문이 끝난 뒤 다음 단계를 순서대로 발화한다.

1. L0: 현재 턴의 원문과 도구 근거를 private memory로 캡처한다.
2. L1: L0에서 다시 쓸 가치가 있는 사실·선호·제약·사건을 원자 단위로 증류한다.
3. L2: 프로젝트나 업무를 재개할 때 복원할 장면을 L1에서 구성한다.
4. L3: 프로그램이 같은 subject의 활성 L1/L2 근거 수를 먼저 검사한다. 최소 두 개가 있을 때만 LLM에 Persona 검토를 발화한다.
5. runbook 제안: 완료·commit·push·pull request 또는 반복 가능한 운영·복구 작업의 완료 신호가 있는지 검토하고, 신호가 있으면 같은 작업 단위에서 생성 여부를 한 번 묻는다.

L0–L2는 `memory.capture: hook`일 때만 발화한다. L3와 runbook은 각각 `hooks.l3.enabled`, `hooks.runbook.enabled`로 끌 수 있다.

## 완료 신호와 사용자 선택 경계

Stop이 발생했다는 이유만으로 runbook을 만들거나 질문하지 않는다. 훅은 최초 완료 메시지와 현재 작업을 보존하고 다음 신호가 있는지 검토하게 한다.

- 기능 구현과 검증 완료
- commit 또는 push 요청·완료
- pull request 생성·갱신·병합
- 배포, 장애 복구, 데이터 이관처럼 다시 실행할 가능성이 있는 작업의 완료

신호가 있으면 AI는 `이번 작업을 인수인계용 runbook으로 남길까요?`라고 한 번 묻는다. 같은 작업 단위에서 완료 뒤 commit과 push가 연달아 일어나도 다시 묻지 않는다. 사용자가 `건너뛰기`를 선택하면 새로운 변경이 생기기 전까지 같은 작업으로 다시 묻지 않는다.

훅의 제안 단계에서는 runbook 파일을 만들거나 기존 파일을 갱신하지 않는다. 사용자가 `만들기`를 명시적으로 선택한 뒤에만 LLM이 반복 가능한 운영·복구 절차가 실제로 생겼는지 확인하고 새 `draft`를 만들거나 기존 runbook의 새 버전을 준비한다. 아직 검증 중인 가설, 일회성 대화와 단순 선호는 runbook으로 승격하지 않는다. 사람의 확인 전에는 `active`로 바꾸지 않는다.

## L3의 프로그래밍 경계

코드는 Persona 내용을 만들지 않는다. 동일 subject에서 활성 L1/L2 문서 ID가 `hooks.l3.minimum_sources` 이상인지 계산해 발화 가능성만 연다. LLM은 후보가 서로 파생된 동일 사건인지, 서로 다른 작업에서 반복된 안정적 선호인지 확인한 뒤 L3 생성 여부를 결정한다.

## 실행 위치

`hooks.execution`은 다음 값을 사용한다.

- `same_thread`: 현재 스레드에서 후처리한다.
- `agent`: 독립 에이전트 위임을 먼저 요청하고, 런타임이 에이전트를 지원하지 않으면 현재 스레드로 폴백한다.

Codex의 command 훅 자체는 에이전트를 직접 생성하지 않는다. 훅이 continuation prompt를 발화하고, 활성 런타임의 에이전트 도구가 실제 위임을 담당한다.

## 설치와 상태

- 전역 훅 정의: `~/.codex/hooks.json`
- 전역 훅 실행기: `~/.codex/hooks/lmwiki_hook.py`
- 세션 상태: `.knowledge/hooks/state/`

상태 파일은 Git에서 제외한다. 전역 훅은 현재 경로에서 가장 가까운 LMWiki 저장소를 사용하며, 없으면 전역 설치 때 지정한 중앙 위키를 사용한다. 중앙 위키도 없을 때만 아무 출력 없이 종료한다. Codex에서 `/hooks`로 전역 훅을 검토하고 신뢰해야 실행된다. `SessionEnd`는 모델을 계속 실행할 수 없으므로 미완료 runbook 제안 검토를 상태에 보류하고, 같은 세션의 다음 `SessionStart`에서 다시 발화한다.
